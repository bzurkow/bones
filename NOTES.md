## Notification aggregation approach (obsolete — see "Product pivot")
Chose service-API integration (Gmail API, Slack API, Discord, Calendar, etc.) over OS-level notification interception — more reliable, more maintainable, one integration per source instead of fragile/restricted OS hooks (esp. on macOS).

## Connector architecture (obsolete — see "Product pivot")
Each source is a **connector** with one contract: call `emit(normalizedNotification)` when something new shows up. Everything downstream (local store, event bus, UI) only ever consumes `emit()`'d notifications and doesn't know how a connector gets its data. This makes the ingestion mechanism swappable per source without touching the rest of the app:
- **v1**: connector polls the source's REST API on a timer, diffs against last-seen IDs/timestamps.
- **v2**: connector opens a WebSocket/SSE connection to our own backend relay (which holds the actual webhook subscription from the source), pushes to `emit()` when the relay forwards an event.

Connector logic lives in TypeScript (not Rust) — better SDKs for Gmail/Slack/Discord etc. Rust/Tauri is reserved for OS-level integration (secure token storage via OS keychain, system tray, native OS notifications).

## Auth requirements (this app's own login — see "Product pivot" for the second, unbuilt SSO-for-generated-apps surface)
- No unauthenticated use — the whole app UI gates on a valid session before rendering anything.
- SSO login required. Start with **Google**, but architecture must support adding any provider (Microsoft, GitHub, Apple, etc.) without rework.
- Two distinct OAuth uses to keep separate: (1) "Sign in with Google" for identity/login, (2) Gmail API access for pulling notifications (broader scope, requested as incremental/separate consent, not bundled into login) — **this second one was specific to the old notification-aggregator product and no longer applies.**
- Desktop auth flow: Tauri app opens system browser → backend `/auth/<provider>` → backend completes OAuth, creates/looks up user, issues its own session token → redirects to a custom protocol (`bones://callback`) Tauri catches → session token stored in OS keychain. **Also obsolete** — Tauri was dropped entirely on 2026-08-31, see "Repo restructure" above.
- User's own data lives in our own DB, keyed off the auth provider's `user_id`.

## Chosen stack

**Desktop shell**: Tauri (Rust-backed, not Electron) — much smaller binaries/lower memory than Electron via native OS webview (WebView2/WKWebView/WebKitGTK), and Tauri v2 adds iOS/Android support if mobile is ever in scope. Runs a React frontend inside.

**Backend language**: Node + TypeScript (user's strongest language).

**API layer**: Fastify + tRPC. tRPC gives end-to-end type safety between the TS backend and TS/React client with minimal boilerplate (no hand-maintained REST schemas). Fastify handles the raw HTTP surface tRPC doesn't cover — OAuth callback redirects and incoming webhooks from third parties (Slack, Discord, etc.), since those are hit by external services, not our typed client.

**Database**: PostgreSQL, hosted on **AWS RDS** — see "Data layer" and "Hosting philosophy" below for the full reasoning.

**ORM**: Drizzle — modern, lightweight, no separate query-engine binary (unlike Prisma), SQL-like syntax, strong TS type inference, `drizzle-kit` for migrations. (Prisma considered as the more turnkey/batteries-included alternative — bigger ecosystem, Prisma Studio GUI — but Drizzle is the more current pick.) Note: Drizzle itself is Postgres/SQL-oriented — if the relational-DB choice below changes to something non-Postgres, revisit whether Drizzle is still the right ORM too.

**Auth provider**: **Better Auth**, embedded directly in `apps/backend` — a library, not a separate service, running inside the same Fastify process. Chosen over Auth.js for its more direct/actively-maintained Fastify integration story, and over standalone self-hosted IdPs (Authentik, Zitadel, Keycloak) to avoid running/operating a second service. No SaaS vendor, no free-tier pause risk, we own storing users/sessions in our own DB. (DB host: AWS RDS — see "Data layer" below.)

**Design system**: undecided. Candidates:
- **shadcn/ui** — probably the current go-to/default in the React ecosystem, but ships as vendored source copied into the repo via CLI rather than a normal versioned npm package.
- **Radix UI** — unstyled/headless primitives installed as normal versioned npm packages (`@radix-ui/react-*`), so it stays managed through `package.json`/lockfile like the rest of the dependency tree; would need a separate styling approach (Tailwind, CSS Modules, etc.).

## Routing
React Router, using `BrowserRouter` (switched from `HashRouter` on 2026-08-31, once Tauri was dropped — `HashRouter` existed specifically because Tauri serves the built frontend as static assets over a custom protocol, not a real server that rewrites arbitrary paths back to `index.html`, and `BrowserRouter`'s real-URL routing 404s on refresh/deep-link without that. With Tauri gone that constraint is gone too, and real URLs (no `#`) are worth it for a browser-only app: shareable/bookmarkable links, no `callbackURL` fragment-appending workaround in the OAuth flow (see `Login.tsx`).

**Whenever this actually gets deployed** (S3 + CloudFront per "Hosting philosophy" below), the static host needs to be configured to rewrite unknown paths back to `index.html` (CloudFront: custom error response, 403/404 → `index.html`, 200) — `BrowserRouter` depends on that; Vite's own dev server already does it automatically, which is why this hasn't needed solving yet. If Tauri ever comes back, this tradeoff needs revisiting too — it's the same doesn't-rewrite-paths constraint that motivated `HashRouter` originally.

Auth gate: `RequireAuth` in `App.tsx` (element-based, wraps only the routes that need it via `<Outlet />`, not the whole `<Routes>` tree) rather than a wrapper around everything with a hardcoded `/login` path exception. Redirects to `/login` with `state: { from: location }` so `Login.tsx` can send the user back to where they were headed instead of always landing on `/`.

## Local-polling-to-backend migration plan
Mandatory auth means a backend exists from day one (for auth + user DB), but notification **polling** itself can still run client-side in v1, using tokens brokered/stored via the backend rather than purely local. Moving actual polling/webhook handling server-side later is a swap of connector internals only, not a rearchitect.

## Scaffolding plan (superseded — see "Repo restructure" below)
Single monorepo (yarn workspaces) so tRPC types can be shared end-to-end between backend and clients without publishing packages:
- `apps/tauri` — the Tauri shell (the native/OS-level bits: window, system tray, OS keychain), thin wrapper that mounts `packages/react-ui`. One project, multiple build targets — desktop **scaffolded**; iOS/Android are additional targets on this *same* project (`tauri ios init`/`tauri android init`), not separate apps. Renamed from `apps/desktop` once mobile made that name inaccurate.
- `apps/web` — plain Vite + React web build, thin wrapper that mounts `packages/react-ui`. Exists so the same UI can run in a browser tab, no Tauri/native layer.
- `packages/react-ui` — the actual shared React app (routes, screens, components) that both `apps/tauri` and `apps/web` import and render. Only the auth glue differs per-shell (system browser + OS keychain for desktop vs. standard redirect + cookie for web) — everything else lives here once.
- `apps/backend` — Fastify + tRPC API, Drizzle schema/migrations, OAuth callback + webhook HTTP routes.
- `packages/shared` — shared TS: tRPC router types, normalized notification schema, connector interface (the `emit()` contract).
- `packages/connectors` — per-source connector implementations (Gmail, Slack, Discord, Calendar, …), each implementing the shared connector interface.

Setup order: `apps/backend` skeleton (Fastify+tRPC, health route, Docker/hot reload — unblocked, no dependency on prod hosting) → Drizzle pointed at local Postgres-in-Docker → Better Auth wired up (Google) → wire `apps/tauri`/`apps/web` to backend tRPC client + real auth flow → first connector. Production AWS RDS deploy happens separately, at actual deploy time.

## Dependency management convention
Shared deps used identically across workspaces (`react`, `react-dom`, `typescript`, `vite`, `@vitejs/plugin-react`, `@types/react`, `@types/react-dom`, `oxlint`) are declared **once, at the root `package.json`**, and hoisted to every workspace via yarn workspaces rather than re-declared per app — avoids the version drift we hit when `apps/web`'s scaffold pulled a different `typescript` than `apps/tauri`. Only genuinely package-specific deps (e.g. `@tauri-apps/*` in `apps/tauri`) stay local. `syncpack` (`yarn deps:check` / `yarn deps:fix`) lints for any version mismatch that creeps back in across workspaces.

**Revisited in the 2026-08-31 restructure**: with `frontend` now the only consumer of `react`/`vite`/`@vitejs/plugin-react`/`@types/react`/`@types/react-dom`, the "avoid drift across multiple consumers" rationale no longer applies to those — they moved into `frontend/package.json` directly, alongside `better-auth` and `@tauri-apps/*` (also only used there). Root `package.json` now holds only genuinely repo-wide tooling: `typescript`, `oxlint`, `syncpack`, `@types/node` (needed by both `backend`'s runtime types and `frontend`'s Node-context `vite.config.ts`).

## Linting
**Oxlint** (Rust-based, part of the Oxc toolchain) — dramatically faster than ESLint since it's a native binary, though fewer rules/smaller plugin ecosystem. Adopted because `create-vite`'s `react-ts` template defaults to it now; kept it and made it consistent across the whole monorepo rather than mixing linters per app. One shared `.oxlintrc.json` at repo root; each workspace has a `lint` script pointing at it (`oxlint -c ../.oxlintrc.json .`).

Rules on top of the defaults, in `.oxlintrc.json`:
- `func-style: ["error", "declaration"]` — `function foo() {}` over `const foo = () => {}` for readability. Verified oxlint actually enforces it (not just a recognized-but-ignored name) before relying on it.

## TypeScript config convention
Same single-source-of-truth idea as dependencies: a root `tsconfig.base.json` holds compiler options shared across every workspace (strict mode, `target`/`lib`, `jsx`, bundler module resolution, unused-locals/params checks). Each workspace's `tsconfig.json` (or `tsconfig.app.json`/`tsconfig.node.json` for split browser/Node contexts, e.g. app code vs. `vite.config.ts`) does `"extends": "../tsconfig.base.json"` and only overrides what's genuinely different for that context (e.g. `types: ["node"]` + `module: "nodenext"` for the Node-context config that type-checks `vite.config.ts`, ambient `vite/client` types for app code). Fixes the drift we'd already gotten from two different scaffolders (`create-tauri-app` vs. `create-vite`) picking different `target`s and one of them silently missing `strict: true`.

## Formatting
No formatter configured yet (oxlint is a linter, not a formatter — doesn't cover code style/whitespace). Open gap, not yet decided (e.g. Prettier).

## Version policy (pre-v1)
Everything built between now and v1 targets the **latest stable version** available at the time it's added — language runtimes, Docker base images, every dependency — not whatever a scaffolder or habit defaults to. Caught in practice: a Dockerfile draft used `node:22-slim` out of habit despite already running Node v26.5.0 locally (nvm) and `@types/node@^26.1.1`. Once the app actually reaches v1, this policy is expected to relax toward more conservative, deliberately-pinned versions — chasing latest on a shipped/stable product is a different tradeoff than chasing it while still building.

Versions must also **match across the app**, not just each be independently "latest." `syncpack` already covers this for JS/TS deps across the yarn workspace. The Node *runtime* version needs the same treatment once Docker is in play: a single root `.node-version` is the source of truth (chosen over `.nvmrc` — same idea, but also read natively by `fnm`/`nodenv`/GitHub Actions, not just `nvm`, which matters given the cross-platform-team goal), and the Dockerfile takes the version as a build arg read from it rather than hardcoding `FROM node:X` a second time — one number to bump, not two that can drift. Caveat: `nvm` itself doesn't read `.node-version` automatically, so local use is `nvm install $(cat .node-version)` rather than a bare `nvm use`.

## Backend validation approach
Layered smoke checks, each isolating one piece so a failure points at exactly what broke, added *as* each piece is built rather than as a test suite after the fact:
1. Container boots — `docker compose up`, Fastify logs it's listening.
2. `/health` — plain Fastify route (not tRPC), proves the HTTP server is alive independent of tRPC/DB/auth.
3. A trivial tRPC procedure (e.g. `health.ping`) — proves the tRPC adapter/router wiring specifically.
4. A DB-touching procedure (`SELECT 1` via Drizzle) — proves the DB connection + Drizzle setup, independent of which host we land on.
5. An auth-gated procedure — once OAuth exists, proves Better Auth + our session verification end to end.
6. A `/debug` route in `packages/react-ui` with buttons wired to each procedure above, showing raw responses on screen — exercises the *real* client→backend pipe from both `apps/tauri` and `apps/web` (both mount `packages/react-ui`), not just the backend in isolation. Gated on `import.meta.env.DEV` so it never ships in production builds.

**Migrations on boot (2026-08-31)**: `backend`'s four `db:*` scripts (`db:generate`, `db:migrate`, `db:studio`, `db:auth:generate`) stay as-is, but `db:migrate` is no longer something you run by hand for local dev — the Dockerfile's dev-stage `CMD` runs `yarn db:migrate && yarn dev`, so every `yarn backend:dev` brings the DB to the current schema before starting the server. `db:generate`/`db:auth:generate` stay manual on purpose (schema-authoring steps needing human review of the generated output before it's committed); `db:studio` stays manual since it's an on-demand GUI. This needed `docker-compose.yml`'s `postgres` service to get a real `pg_isready` healthcheck and `backend`'s `depends_on` to wait on `condition: service_healthy` instead of just container-started — otherwise migrate could race Postgres actually accepting connections.

## Hosting philosophy
**Single cloud provider: AWS hosts everything.** Explicit preference — operational simplicity of one vendor/one bill/one console over chasing best-per-service pricing or features across multiple providers. Applies to anything actually *hosted* (compute, managed DB, container registry, static assets); doesn't apply to things that aren't hosted anywhere by nature — local dev tools (OrbStack, Drizzle Studio) run on your own machine, and Better Auth is code embedded in our own backend, not a separate vendor. Concrete implications: container images go to **ECR**, not Docker Hub; `apps/web` static hosting is S3 + CloudFront (already the plan); DB hosting below narrows to AWS-only options.

## Data layer — DB hosting decided; auth decided
Supabase was bundling two separate decisions (Postgres host + Auth provider) into one vendor. Revisited both, partly triggered by Supabase's free-tier auto-pause-on-inactivity behavior (projects pause after ~1 week idle, need a manual un-pause).

**Auth: decided — Better Auth**, embedded in `apps/backend` (see "Chosen stack" above). Options considered along the way:
- **Auth.js (NextAuth)** — self-hosted, no SaaS vendor, huge library of prebuilt provider configs, but no first-class official Fastify integration found — likely needs a small adapter bridging Fastify's req/res to its Fetch-based core.
- **Better Auth** ✅ — same self-hosted/no-vendor shape as Auth.js, chosen for its more direct Fastify integration story.
- **Standalone self-hosted IdPs** (Authentik, Zitadel, Keycloak) — more built-in admin/user-management UI, but each is a separate service to run and operate on top of the DB decision below; ruled out to avoid that extra ops surface.
- **Clerk / Auth0** — polished SaaS, but another usage-limited free tier and vendor dependency, same shape of risk as Supabase.
- **Firebase Auth** — generous free tier, easy SSO, but pulls in Google's ecosystem and doesn't naturally pair with a self-hosted Postgres backend.

**DB hosting: decided — AWS RDS PostgreSQL.** Given the "AWS hosts everything" preference above, Neon/Railway/Render are ruled out outright (all non-AWS vendors) without needing to weigh their individual tradeoffs further. Options considered along the way:
- ~~Neon~~ / ~~Railway~~ / ~~Render~~ — all ruled out solely on the single-provider preference, not on their individual merits (which were otherwise reasonable).
- **AWS RDS PostgreSQL** ✅ — the standard fully-managed AWS Postgres, has a genuine (if time-limited, 12 months) free tier, no surprise pausing. Chosen over Aurora specifically: Aurora's benefit is scale/performance headroom this project doesn't need yet, at a real price premium with no meaningful free tier. RDS fits the actual stated motivation (ease) better than Aurora does.
- **Amazon Aurora PostgreSQL** — noted as the natural upgrade path later, not ruled out permanently. Wire-compatible with standard Postgres, so moving to it if/when scale demands it is a bigger instance type, not a migration.
- **Postgres in Docker (self-hosted, forever)** — technically satisfies "one provider" if run on AWS compute, but ruled out because it works against the actual motivation: it trades away RDS's managed backups/HA for us owning that ops burden ourselves, which is the opposite of "easier."

Doesn't block current backend work either way: local dev still runs Postgres in Docker regardless of the production host, so this only matters at actual deploy time.

## Google sign-in broke on the app.localhost dev convention (2026-09-07)
Google sign-in from `web-app` (`yarn web-app:dev`, tested for the first time in a while) failed with `state_mismatch` on every single attempt, 5-35 seconds after clicking "Continue with Google" -- fast enough to rule out the OAuth `state` cookie's own 5-minute expiry outright. Root cause, confirmed with hard evidence rather than guessed: the `app.localhost:5173` dev convention (see the "Workspace folder rename" entry above -- introduced with the marketing-site split, `web-app/vite.config.ts`'s `allowedHosts`) meant `web-app` (`app.localhost:5173`) and `backend` (`localhost:3000`) were now different hostnames, not just different ports of the same host like before. Better Auth's OAuth `state` cookie is host-only by default -- confirmed via `curl` that presenting the exact right `state` param without that cookie reproduces `state_mismatch` immediately, and presenting it with the cookie gets past validation (fails later, at `invalid_code`, as expected with a fake code) -- so the browser was provably not carrying that cookie from the cross-host sign-in request through to Google's callback.

Two things this was *not*, ruled out with direct evidence before landing on the real fix:
- **Not a stale/expired cookie** -- every failure was 5-35 seconds after clicking, nowhere near the cookie's 300s `Max-Age`.
- **Not a Google Console misconfiguration** -- the backend's own logs showed Google's redirect actually reaching `/api/auth/callback/google` with a real code+state every time; a bad `redirect_uri` registration would have stopped at Google's own `Error 400: redirect_uri_mismatch` page and never reached our server at all.

First fix attempt -- `better-auth`'s `advanced.crossSubDomainCookies` alone (broadens the cookie's `Domain` from host-only to a parent domain covering both hosts) -- did not fully resolve it in a real browser. Broadening `Domain` doesn't help if the browser refuses to persist/replay the cookie at all because the *setting* request itself (the initial sign-in `fetch()` from `app.localhost` to `localhost:3000`) is cross-host -- exactly the shape third-party-cookie blocking targets, independent of what the cookie's `Domain` claims.

Second attempt -- move `BETTER_AUTH_URL`/`VITE_BACKEND_URL` to `app.localhost:5173` entirely, so everything (including Google's own redirect_uri) shares one hostname -- fixed the cookie problem but broke a completely different, Google-side rule: **Google's OAuth redirect-URI/JS-origin validation only exempts bare `localhost`/`127.0.0.1` from its HTTPS/domain-verification requirements** (confirmed via Google's own docs, and directly via a real `Error 400: invalid_request ... redirect_uri=http://app.localhost:5173/...` when this was actually tried against a fresh Google Cloud project). `app.localhost` was never going to be accepted as a registered redirect URI at all, no matter what.

**Final fix** -- both constraints turned out to need different halves of the stack pointed at different hosts:
- `web-app/vite.config.ts` gained a `server.proxy` forwarding `/api` and `/trpc` to `http://localhost:3000` -- so the browser's own fetches (including the one that sets the `state` cookie) stay same-origin against `app.localhost:5173`, avoiding the third-party-cookie problem at the *setting* step.
- `BETTER_AUTH_URL` stayed bare `http://localhost:3000` (not moved to `app.localhost`) -- so Google's redirect_uri stays on the one hostname Google actually allows. Google's own redirect back is a real top-level navigation Google initiates directly at `localhost:3000`, entirely unproxied.
- `VITE_BACKEND_URL` moved to `http://app.localhost:5173` (so `web-app`'s own client code routes through the new proxy rather than fetching `localhost:3000` directly).
- `backend/src/auth.ts` re-gained `advanced.crossSubDomainCookies: { enabled: true }` (domain defaults to `BETTER_AUTH_URL`'s own hostname, `localhost`) -- needed because the cookie still has to be valid on *both* hosts: same-origin via the proxy for the initial set, and directly on bare `localhost:3000` for Google's unproxied callback.

Verified end to end with a real sign-in before landing here. Also created a brand-new Google Cloud project along the way (to fix the OAuth consent screen's name, previously the scaffold-default "Platypus Test" -- separate, unrelated fix) -- its Authorized JavaScript origin is `http://app.localhost:5173`, redirect URI is `http://localhost:3000/api/auth/callback/google`.

## S3 file storage scaffold (2026-09-08)
Roadmap item 5 ("Large file storage") turned from an undetailed backlog entry into a working scaffold: local-dev S3-compatible storage, env-var wiring to swap to real AWS S3 in production with zero code changes, and a minimal backend client module ready for the first real upload feature. No concrete upload feature exists yet -- infrastructure only, same shape as how Postgres/Drizzle were scaffolded before any feature used them.

**Local dev tooling was a real decision, not a default.** Both usual go-tos are 2026 dead ends: LocalStack was archived with no mature successor yet; MinIO's open-source edition was also archived (April 2026) -- maintenance-mode/security-fixes-only, lost its web console, split into a paid enterprise tier. Landed on **RustFS** (Apache 2.0, single container, built specifically as a MinIO replacement) as the least-bad current option. Caveat, stated plainly: RustFS is itself pre-GA (`v1.0.0-rc.5`, working toward stability per its own roadmap) -- real tension with this file's own "Version policy (pre-v1)" latest-*stable* rule. Accepted because it's local-dev-only, never touches production, and swapping it later (SeaweedFS, or dropping local emulation for a real AWS dev bucket) is purely a `docker-compose.yml` service change -- application code only ever talks to a standard S3-compatible endpoint via env vars, never to RustFS specifically.

Concrete pieces:
- `docker-compose.yml` -- new `rustfs` service, same pattern as `postgres` (pinned image tag, named volume, healthcheck gating `depends_on`). `backend` now waits on both `postgres` and `rustfs` being healthy.
- New env vars (`.env`/`.env.example`): `AWS_REGION`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` (the AWS SDK's own default env var names -- auto-detected with zero explicit `credentials` config), `S3_BUCKET`, and `S3_ENDPOINT`/`S3_FORCE_PATH_STYLE` (dev-only -- unset in production, where the SDK falls back to real AWS endpoints/virtual-hosted-style addressing on its own).
- `backend/src/storage/index.ts` (new) -- mirrors `backend/src/db/index.ts`'s minimal client-setup shape: a configured `S3Client` plus `getPresignedUploadUrl`/`getPresignedDownloadUrl` helpers (`@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`, SDK v3 -- the only version consistent with this stack's ESM/latest-stable conventions, unlike the monolithic CJS/legacy SDK v2). Presigned URLs, not backend-proxied uploads, per current uncontested best practice -- the backend issues a short-lived signed URL, the browser uploads directly to S3, AWS credentials never reach the client. Also auto-creates the dev bucket on import if `S3_ENDPOINT` is set (mirrors "migrations run on every boot" -- zero manual setup from a fresh clone; gated so this never runs against real production AWS). No tRPC router yet, deliberately -- matches this repo's "build as features need it, not speculatively" pattern; the client + presigned-URL helpers are the reusable boilerplate, an actual upload feature gets its own router when one exists.

Verified end to end (not just "it compiles"): brought up the full stack from a completely fresh volume (`docker compose down -v && up`), confirmed `rustfs`'s healthcheck passes and `backend` waits on it correctly, then ran a throwaway script inside the running container exercising the real chain -- `getPresignedUploadUrl` → real `PUT` via `fetch` → `getPresignedDownloadUrl` → real `GET` → content round-tripped byte-for-byte. Confirmed bucket auto-creation is idempotent (clean re-run, no "already exists" crash) both immediately and from a second fresh-volume boot.

`docker-compose.yml` → `docker-compose.dev.yml` right after this landed -- everything in it (`postgres`, `rustfs`, and `backend` running in its dev-hot-reload `target`) is local-dev-only, never how anything actually gets deployed, so the name should say so rather than imply it's the one true compose file. `COMPOSE_FILE` can't be set via `.env` to make bare `docker compose` commands keep working -- genuine chicken-and-egg problem, Compose has to find *a* compose file before it can read any `.env` to learn `COMPOSE_FILE`'s value, confirmed via Docker's own docs. Every invocation needs an explicit `-f docker-compose.dev.yml` instead: updated in `package.json`'s `backend:dev` script and `scripts/initialize-backend.sh`'s `docker compose run`, the only two call sites in the repo.

## Terms & Conditions: table, routes, session field (2026-09-08)
First real domain tables in the repo (`db/schema.ts`'s "one file per table" comment finally has something to point at): `terms_and_conditions` (`id`, `assetUrl`, `active`, `addedBy` → `users.id`, `termsAndConditionsAttribution`, `createdAt`) and a join table, `user_terms_and_conditions` (`termsAndConditionsId`, `userId`, `accepted`, `acceptedDate`, composite primary key on the two FKs -- no synthetic id, nothing else could meaningfully identify a row).

**Versioned, not mutated in place**: `active` being a per-row boolean (not a single mutable settings row) is the tell -- an "update" inserts a *new* `terms_and_conditions` row and flips the previous one's `active` off in the same `db.transaction()`, so there's a real history of exactly what each user's acceptance row points at, not just whatever the current text happens to be. `trpc/routers/terms-and-conditions.ts`: `get` (public -- a signup page or similar needs this without a session) resolves the stored asset key to a real presigned URL before returning; `update` (new `adminProcedure` in `trpc.ts`, same role check as `web-app`'s `isAdmin`, `FORBIDDEN` not `UNAUTHORIZED` since `protectedProcedure` already established there's a session) takes the new version's markdown directly in the mutation input -- not a presigned client upload, since this is small trusted text from an already-authenticated admin, not a user uploading a file of their own -- and calls a new `uploadObject` direct-upload helper added to `storage/index.ts` alongside the existing presigned-URL ones.

**`hasAcceptedTermsAndConditions` on every session** (`auth.ts`'s new `customSession` plugin, `better-auth/plugins`): whether the currently-active version (if any) has an accepted row in the join table for this user; vacuously `true` when nothing's active. Query logic lives in its own `terms-and-conditions.ts` (not inside the trpc router file) specifically so `auth.ts` can import it without a cycle through `trpc.ts` (which itself imports `auth.ts`). Hit a confirmed upstream typing gap doing this: `customSession`'s callback param doesn't carry `user`'s `additionalFields` (role/viewMode/etc.) even though they're genuinely present at runtime -- [better-auth/better-auth#3888](https://github.com/better-auth/better-auth/issues/3888), not a mistake here. Fixed with one cast right where the plugin's `Returns` generic gets inferred (in the callback, re-typing `user` once) so the correct shape flows to every downstream consumer of `auth.api.getSession()` -- notably `trpc/trpc.ts`'s new `adminProcedure` -- instead of every caller needing its own cast.

## Shared Table component + admin users table (2026-09-10)

**A CSS Grid "table," not a real `<table>` element.** The ask was resizable columns that start flex-sized (`minmax(minWidth, 1fr)`) and become fixed-px once dragged -- `grid-template-columns` expresses that mix natively; native `<table>` layout algorithms fight it. Resize is a small hand-rolled `pointerdown`/`pointermove`/`pointerup` drag on each header cell's right edge -- no library, self-contained enough not to need one.

**Search, sort, and pagination all had to become server-side together**, not because each was independently asked for that way, but because they're coupled once pagination is real: once only one page of rows is ever fetched, a client-side filter/sort would only ever apply to whatever page happened to already be loaded -- search would silently miss most of the dataset, sort would only reorder 25 rows. `admin.listUsers` (`backend/src/trpc/routers/admin.ts`, new) takes `page`/`pageSize`/`search`/`sortBy`/`sortDirection`, does a real `ILIKE` over name/email plus a real `ORDER BY`, and returns `{ users, total }`. `sortBy` goes through a small server-side allowlist (`SORTABLE_COLUMNS`, mapping a plain string key to the real Drizzle column) rather than any raw column-name lookup from client input -- both for safety and because it's the seam a future calculated column (no single backing DB column) would extend later without the `Table` component's own API (`enableSort: boolean`, an opaque sort-key string) needing to change at all. `Table` itself stays presentational -- it never fetches; `AdminUsers.tsx` owns the actual `trpc.admin.listUsers` call, debouncing search (`@mantine/hooks`' `useDebouncedValue`, 300ms) before it becomes a request and resetting to page 1 whenever the debounced term changes.

## RBAC: roles, features, feature_roles (2026-09-11)
`bones-roadmap-notes.md` item 3, deferred since 2026-09-03: `users.role` was a hardcoded 4-value TypeScript enum (`backend/src/user-fields.ts`'s `USER_ROLES`), and every admin-gating check (`trpc.ts`'s `adminProcedure`, `web-app/src/AuthHelpers/roles.ts`'s `isAdmin`) was a literal `"owner" || "administrator"` string compare. Full design reasoning lives in that plan; this entry is the as-built account plus what changed from it during implementation.

**Schema**: three new tables, `backend/src/db/{roles,features,feature-roles}-schema.ts`. `roles` (`name text PK`, no other columns -- `roles.ts`'s `delete` procedure hardcodes `owner`/`standard` as permanently undeletable rather than a DB flag, same ad hoc-guard style as this app's other self-lockout checks). `features` (`key text PK` -- a stable, code-referenced slug like `admin.users.view`; `label`; `enabled boolean` -- a global kill switch, independent of any role, deliberately the *same* table RBAC and feature-flagging both key off rather than two tables kept in sync). `feature_roles` (composite PK `(feature_key, role)`, real `.references()` FKs to both, `granted boolean` -- a plain boolean, not a none/read/write level; granularity comes from defining many narrow features, not a tri-state on one coarse one -- this diverged from the roadmap note's original "none/read/write" framing once the user supplied an actual sketch of the real permission matrix wanted).

## "View as role" preview toggle (2026-09-11)
Same day, the follow-up item the RBAC entry above deliberately left out (hard ordering dependency -- nothing to preview until the permission matrix was real). Built exactly to the plan file's spec: a floating button group, bottom-right, left of the existing `ColorSchemeToggleButton`, owner-only, letting the current user preview the app as if a different role were signed in -- **rendering only**, never a real authorization change (every actual tRPC call still runs under the real session's real permissions the whole time; see `ViewAsRoleToggle.tsx`'s own comment on why a real server-side impersonation mode was deliberately not what got built).

**Gating, two layers**: hardcoded to `role === "owner"` (never permission-table-driven itself -- it's the tool for *previewing* the permission table, same bootstrap-role treatment `nextUserRole` already gets), and within that, a new per-user `showViewAsRoleToggle` setting (`auth.ts` `additionalFields`, same shape as `showViewModeToggle`, default `true`) controls whether the button renders at all. `ApplicationSettings.tsx` gained a matching switch, shown only when `session.user.role === "owner"`. New migration `0012_watery_viper.sql` -- a single clean `ALTER TABLE users ADD COLUMN`, no hand-editing needed this time (unlike the RBAC migration's `users.role` FK, this column is a plain Better Auth-generated field like `showViewModeToggle` already was).

**State is deliberately ephemeral, not a DB column**: `previewRole: string | null` lives in a new React context (`ViewAsRoleContext.tsx`), persisted to `localStorage` only (same per-viewer-convenience category as `ColorSchemeToggleButton`'s own browser-only fallback) -- there's nothing else that needs to read which role is currently being previewed, and it should reset naturally rather than surviving across devices/sessions. Split into three files once oxlint's `react-refresh` rule flagged the first draft (a single file exporting both the `ViewAsRoleProvider` component and the `useViewAsRole` hook) -- `view-as-role-context.ts` now holds just the raw `createContext` call, `ViewAsRoleContext.tsx` exports only the Provider, `hooks/useViewAsRole.ts` exports only the hook.

**The actual preview mechanism**: `hooks/useEffectivePermissions.ts` returns `session.enabledFeatures` normally, or -- when a preview role is active -- a derived list computed client-side from the exact same `features.list`/`featureRoles.listAll` data `AdminPermissions.tsx`'s grid already fetches (no bespoke endpoint added). Every `page.*`-gated check in the app now reads through this hook instead of `session.enabledFeatures` directly: `App.tsx`'s `RequireAdmin`, `TopBar.tsx`'s admin menu item, `AdminLayout.tsx`'s tab filtering. `AuthHelpers/permissions.ts`'s `hasFeature` signature changed from taking a whole session object to taking a plain `string[]` -- simpler, and the right shape for a function that now needs to work against either the real or the simulated list interchangeably.

One real consequence worth being explicit about, not a bug: since `RequireAdmin` itself reads through the effective-permissions hook, previewing a role with no `page.admin.view` while already on an admin page immediately navigates the owner away -- the route guard has no way to know "this is just a preview," it treats the simulated permissions as real for rendering purposes, which is exactly the intended behavior ("render as if that role were signed in"), not a glitch to special-case around.

Verified: `yarn workspace backend test` (94/94, includes two new `user-settings.test.ts` cases for the new field, fixed two others whose `toEqual` assertions needed the new field added to their expected shape), `yarn workspace backend build`, `web-app`'s `tsc -b && vite build`, and `yarn lint` all clean. Live against the rebuilt dev stack: confirmed the new `showViewAsRoleToggle` session field defaults to `true` and the settings mutation persists a change to it; since the actual role-preview logic is pure client-side React state with no server round-trip to exercise via curl, verified its derivation instead by fetching the same `features.list`/`featureRoles.listAll` data the hook consumes and manually replicating its exact filter (`enabled && granted`, scoped to one role) for `"administrator"` -- got 15 feature keys back, matching the real `administrator` grant count already confirmed live in the RBAC entry above. Throwaway account cleaned up afterward.

**Follow-up, same day -- two real bugs from actual live usage, not caught by the verification above.** The user hit "I can't access /admin at all" almost immediately, with a genuine `414 URI Too Long` in their console: `RequireAdmin`, `TopBar`, and `AdminLayout` each independently called `useEffectivePermissions()`, and that hook did its own `features.list`+`featureRoles.listAll` fetch per call site -- three (or more, across remounts from navigating in and out of `/admin` while stuck) separate fetches landing in the same tRPC batch window, the batched URL growing until it blew past the limit. Root cause traced from the backend's own request log (`docker logs bones-backend-1`), which showed the exact same procedure pair repeating 4-5 times in one URL -- concrete evidence, not a guess, of what was actually piling up.

Fixed by moving the fetch into `ViewAsRoleProvider` itself -- a singleton, mounted once, never remounted by navigation -- so there's exactly one fetch per `previewRole` change no matter how many components read the result. `useEffectivePermissions` became a thin context reader with zero fetching of its own. This is a strictly better architecture regardless of the exact trigger, not just a patch for this one symptom.

Tracing it surfaced a second, worse bug along the way: while that fetch was in flight, the hook returned an *empty* feature list -- meaning activating a preview from *inside* `/admin` would instantly redirect away even for a role that genuinely has `page.admin.view`, before the real answer ever loaded. `useEffectivePermissions` now returns a real `isLoading` flag; `RequireAdmin` waits for it (shows its existing `Loader`) instead of treating "not yet known" as "denied."

Also made explicit, per a direct request prompted by the confusion: `ViewAsRoleToggle` itself must never read the simulated permissions for its own gating or role list -- it already didn't (both were always real `session.user.role`/`trpc.roles.list`), but the invariant is now a named comment, not just an accident of how it happened to be written, since the one control that turns a preview off can't be allowed to become unreachable while previewing a low-access role -- the same self-lockout-prevention spirit as this app's other ad hoc guards, applied to a new place.

Verified: `yarn workspace backend test` (94/94, unaffected -- no backend changes this pass), `web-app`'s `tsc -b && vite build`, `yarn lint` all clean. Not re-verified live end-to-end against a real stuck preview afterward (would need a browser, unavailable this session) -- the fix is a straightforward architectural correction (one fetch instead of three, a real loading state instead of a false-negative), reasoned through and build/lint-clean, but the user should confirm the actual click-through once they're unstuck.
